## 二、逐字稿

### 0:00–0:15　开场（干什么用的）

> 老师好。我讲的是**车辆智能调度 Agent**。
> 一句话说清它是干什么的：每天门店的货量报上来以后，它算出一张排车表 —— ‖ **哪台车、跑几趟、上午下午分别送哪些门店、每趟装多少货**，然后交给调度员确认、下发。

### 0:15–0:55　需求

> 先说需求。场景是门店配送：每天有一批门店要货，我们有一支车队 —— **四米二 28 台、大包 3 台、小包 9 台，一共 40 台**。
> 需求文档给了 8 条业务约束，最要命的是这四条：
> 第一，**装够最低装载量才能发车** —— 四米二最低 630、最高 800；
> 第二，**上午门店只能上午送，下午门店只能下午送**；
> 第三，车辆有**地形限制** —— 门店分普通、中控、严控，车辆分全能去、大小包能去、小包能去；
> 第四，门店和线路是**多对多**，还有门店卡在几条线路的交界处。
> 另外，货量不够时优先保障大包、小包的出车趟次，车型上优先用四米二；也不保障每天 28、3、9 台满勤，可以动态调节。

### 0:55–1:25　为什么要做这个项目

> 为什么要做？因为**这件事人工已经排不动了**。
> 40 台车、十几个门店、上下午两个时段，每一条约束都在互相顶：你想装满一辆四米二，就得把两三个门店拼到一趟，可拼到一起之后 —— 可能地形不让过、线路对不上，或者其中一个是下午店。‖
> 调度员靠经验排，一次要几个小时；排完还说不清为什么这么排，换个人排，结果完全不一样。
> 所以这个项目的目标不是替掉调度员，而是**把调度员的经验固化成规则，把「排车」从手工劳动变成「选方案」** —— ‖ **人做决策，机器做计算。**

### 1:25–1:55　怎么做（快速带过）

> 实现上是 Vue 3 前端加 FastAPI 后端，28 张表。核心是一个**三阶段混合求解器**：先用启发式毫秒级出一个可行解，保证一定有结果；再用 OR-Tools 的 CP-SAT 按不同目标去优化；最后输出**四套方案** —— A 四米二优先、B 成本最低、C 大包小包保障、D 装载率均衡，每套带评分，横向比选。调度员确认哪一套，再下发；下发做了**幂等**，重复点不会重复派车。中途车辆故障、门店加减货，可以上报异常触发重排，**已经执行过的趟次锁死不动**。

### 1:55–2:50　做项目过程中遇到的问题（重点段）

> 最后讲三个真正卡过我的问题。
>
> **第一个，是需求的空白，不是代码的 bug。**
> 我最初严格按文档实现 —— 一个门店的货量由同一趟车一次送完。结果实测**覆盖率只有 25%**，方案基本不能用。
> 我去翻数据才发现：有个门店日货量是 **2290**，而四米二单车上限只有 **800**，**一趟车物理上就装不下**。
> 需求文档没有禁止拆单，但也没说要拆 —— 这是文档的空白。我跟业务口径核对后，改成**允许一个门店的货量拆到多个趟次**，覆盖率从 25% 提到 **99.8%**。
> 这件事让我记住：**需求文档没写的东西，不等于业务不需要。**
>
> **第二个问题：不能让求解器自己验自己。**
> 求解器内部已经判过那 7 条硬约束了，但我没有拿它的输出去当校验结果 —— 万一求解器本身有 bug，它错的同时也会「认为」自己对，**自己验自己等于没验**。
> 所以我另外写了一个独立的 `validate_solution()`，用完全独立的一套代码把 7 条硬约束重新复核一遍。**求解器的 bug，绝不能被它的校验逻辑掩盖。**
>
> **第三个问题，是取舍：编不出来的数据，我不编。**
> 需求里要求监控 API 的 QPS、P95 延迟、Redis 命中率，还要跟 TMS、WMS、OMS 打通。这些都需要额外的中间件和外部系统，本项目没接入。
> 我的处理是 —— 页面上**如实标注「未接入」「未连通」**，同时说明本地已经落地了哪些链路。
> 因为**编造的监控数据，比没有监控更危险**。‖

### 2:50–3:00　收尾

> 目前 9 大模块里 6 个完整落地，后端 173 项、前端 106 项自检全部可重复通过。
> 一句话总结：**这个项目做的不是排车算法，是把调度经验变成可执行、可解释、可追溯的规则。**
> 谢谢老师。

## 三、要开电脑演示的话（30 秒动线）

只走一条主线，别翻页：

1. **门店配送需求** → 点「生成演示货量」（16 个门店，日货量 19920）
2. **调度任务** → 点「开始调度」→ 出 A/B/C/D 四套方案
3. **多方案比选** → 指着绿色最优值说一句「A 方案 29 趟、15 车、四米二使用率 86.2%，货量满足 100%」
4. **人工确认** → 确认 → 下发 → **再点一次下发**，说：「看，新增 0、跳过 47 —— 这就是幂等」

> 如果时间紧，只演第 4 步的「重复下发」：这一下最能证明你想过工程问题。

## 四、老师可能追问的问题（提前背）

| 可能被问 | 怎么答 |
| --- | --- |
| 为什么用 MySQL，文档写的是 PostgreSQL？ | 本机没有 PG 且 Docker 没起。**代码里没有使用任何 MySQL 方言**，换 PG 只要改 `config.py` 一行 `drivername`。 |
| LLM 到底用在哪？ | LangGraph 节点已就位。**硬约束绝不交给 LLM** —— LLM 只做方案解释和报告的自然语言生成，算错了也不影响可行性。 |
| 允许拆单是不是在回避难点？ | 恰恰相反。拆单把问题变成「货量单元 → 趟次槽位」的分配问题，建模更难。2290 超过 800 是物理约束，不拆就是 25% 覆盖率。 |
| 为什么 D 方案是 99.8%，不是 100%？ | 覆盖率口径是**按货量满足比例**算的。D 方案只有 25 趟、13 台车，尾部凑不满最低装载量的零头会被放弃；A 和 C 是 100%。这个口径差异在报表和自检脚本里都写明了。 |
| 测试怎么做的？ | 后端 6 个脚本 173 项，前端 5 个脚本 106 项，共 **279 项，全部可重复执行**（跑第二遍不会失败）。前端用 Playwright 驱动本机 Chrome，同时收集控制台报错，正常应为 0 条。 |
| 哪些没做？ | 移动端/司机端未实现（需求里定位为独立端）；TMS/OMS/WMS/ERP 全部未真实连通，页面标 `not_connected`；向量库和案例沉淀是规划项。**共 9 大模块，6 个完整、3 个部分完成。** |
| 成本是怎么算的？ | 四米二 1.0 / 大包 0.85 / 小包 0.5，是**相对系数**，只用于方案之间横向比较，不是真实金额 —— 页面上有标注。 |
