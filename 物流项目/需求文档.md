## 一、需求描述

### 1.1 项目背景 📄

本项目面向门店配送场景，需要根据每日门店货量、车辆运力、地形限制、线路映射等条件，智能分配车辆和趟次，输出可执行的配送方案。

### 1.2 功能点

**基础信息维护**

1. 地形限制维护（普通、中控、严控）
2. 门店信息维护
3. 门店线路映射关系维护
4. 车辆类型维护

**车辆分配**

1. 可出勤车辆
2. 门店配送
3. 分配结果

### 1.3 现有条件

| 车型 | 数量 | 最低装载量 | 最高装载量 | 每日最少趟次 | 趟次拆分 |
| --- | --- | --- | --- | --- | --- |
| 四米二 | 28 台 | 630 | 800 | 2 趟 | 上午 1 趟 + 下午 1 趟 |
| 大包 | 3 台 | 300 | 420 | 2 趟 | 上午 1 趟 + 下午 1 趟 |
| 小包 | 9 台 | 1 | 300 | 4 趟 | 上午 2 趟 + 下午 2 趟 |

### 1.4 核心业务约束 📄

技术方案文档对业务约束做了归纳，与随堂笔记一致：

| 约束 | 内容 |
| --- | --- |
| 车辆类型 | 四米二（28 台，装载 630-800，日 2 趟）、大包（3 台，装载 300-420，日 2 趟）、小包（9 台，装载 1-300，日 4 趟） |
| 趟次规则 | 四米二上午 1 趟下午 1 趟；大包上午 1 趟下午 1 趟；小包上午 2 趟下午 2 趟 |
| 发车规则 | 达到最低装载量才发车 |
| 时段规则 | 上午门店上午送，下午门店下午送 |
| 地形规则 | 普通／中控／严控；车辆能力分全能去、大小包能去、小包能去 |
| 线路规则 | 门店与线路多对多，部分门店处于多线路交界 |
| 货量不足 | 优先保障大包、小包日出车次数 |
| 车型优先 | 多种派车方案优先用四米二 |
| 动态调节 | 不保障每天 28／3／9 台满勤，可动态调节 |

### 1.5 需求明细

1. 当货量不够的情况，先保障大包、小包的日出车次数。
2. 上午门店上午送，下午门店下午送。
3. 达到车辆最低装载量，车辆才会进行发车。
4. 多种派车方案优先用四米二车辆。
5. 不保障车辆的满勤状态，可动态调节：也就是不保障每天有四米二的车辆 28 台，每天有大包的车辆 3 台，每天有小包的车辆 9 台。
6. 门店有线路限制，门店与线路是多对多的关系。一个门店可能属于多个线路，一个线路上也有多个门店。
7. 车辆有地形限制情况：
   1. 全能去
   2. 大小包能去
   3. 小包能去
8. 部分门店处于多条线路的交界处。

### 1.6 项目目标 📄

1. 建立基础数据与规则配置中心，实现业务规则可配置、可版本化。
2. 构建智能调度 Agent，实现从数据感知到方案下发、异常重排的全流程自动化。
3. 提供多方案比选、人工确认、可解释的调度结果。
4. 与 TMS 对接，实现调度方案的落地执行与执行结果回传。
5. 提供调度报表、看板和异常监控，支撑运营决策。

```

    │

    │  状态持久化：MySQL / Redis
    │  人工中断：interrupt / Command(resume)

    ├─ 数据感知服务：门店、车辆、线路、地形、货量、规则
    ├─ 规则中心服务：硬约束、软约束、版本快照
    ├─ 调度求解器：OR-Tools CP-SAT / 启发式
    ├─ 评分服务：多方案评分
    ├─ 解释服务：LangChain + LLM
```

## 四、智能调度 Agent 详细设计 📄

### 4.1 LangGraph 工作流节点

| 节点 | 职责 | 关键技术 |
| --- | --- | --- |
| load_task | 加载任务、租户、日期、时间窗 | DB 查询 |
| data_perception | 拉取门店、车辆、线路、地形、货量、规则 | asyncio.gather 并行 |
| constraint_parse | 规则中心配置解析为硬／软约束 | Pydantic 模型 |
| rule_validation | 校验数据完整性、规则冲突、地形冲突 | 确定性校验 |
| plan_generation | 调用求解器生成多方案 | OR-Tools CP-SAT + 启发式 |
| plan_scoring | 方案评分、淘汰硬约束违规 | 加权评分函数 |
| plan_explanation | LLM 生成自然语言解释 | LangChain + LLM |
| human_confirmation | interrupt 等待人工确认 | LangGraph interrupt |
| dispatch_execution | 下发 TMS／司机端，写执行记录 | 幂等接口 |
| report_generation | 生成调度报告 | 聚合 SQL + LLM |
| monitor_exception | 接收异常事件 | MQ 消费 |
| impact_analysis | 分析影响范围 | 图算法 |
| replan | 锁定已执行趟次，局部／全局重排 | 增量求解 |
| relax_constraints | 放宽软约束后重试 | 约束松弛策略 |

**主流程**

```
load_task → data_perception → constraint_parse → rule_validation
  → plan_generation → plan_scoring → plan_explanation
  → human_confirmation → dispatch_execution → report_generation
```

**分支**

- 校验失败 → `exception_handler`
- 无可行方案 → `relax_constraints` → 重试 `plan_generation`
- 人工驳回 → 回到 `plan_generation`

**异常重排入口**

```
异常事件 → monitor_exception → impact_analysis → replan
  → plan_scoring → human_confirmation → dispatch_execution
```

### 4.2 调度求解器设计

**三阶段混合求解**

- **阶段 1：启发式快速生成初始可行解** —— 按地形、线路分组门店；优先保障大包、小包趟次；优先使用四米二；上午／下午分开排趟；贪心装车，满足最低装载量。
- **阶段 2：CP-SAT 优化** —— 对初始解进行局部优化；对关键车辆、关键线路重新求解；多目标优化（四米二使用率、装载率、成本、趟次达成）。
- **阶段 3：多方案生成** —— 方案 A：四米二优先（CP-SAT）；方案 B：成本最低（启发式）；方案 C：大包／小包趟次保障优先（启发式）；方案 D：装载率均衡（CP-SAT）。

**决策变量**

| 变量 | 含义 |
| --- | --- |
| `x[v, t, s]` | =1 表示车辆 v 第 t 趟服务门店 s |
| `y[v, t]` | =1 表示车辆 v 第 t 趟发车 |
| `load[v, t]` | 车辆 v 第 t 趟装载量 |
| `trip_count[v]` | 车辆 v 总趟次 |

**硬约束**

1. 每个门店需求必须满足
2. 上午门店只能上午趟，下午门店只能下午趟
3. 车辆地形能力必须覆盖门店地形
4. 门店必须属于车辆可跑线路
5. 发车必须达到最低装载量
6. 不能超过最高装载量
7. 四米二最多 2 趟，大包最多 2 趟，小包最多 4 趟

**软约束**

- 大包、小包日出车次数优先保障
- 不强制每天 28／3／9 台满勤

**目标函数**

```
maximize:
    w1 * 四米二使用率
  + w2 * 平均装载率
  + w3 * 大包小包趟次达成率
  - w4 * 车辆总成本
  - w5 * 软约束违规惩罚
```

### 4.3 人工确认机制

```python
from langgraph.types import interrupt, Command

async def human_confirmation(state):
    decision = interrupt({
        "task_id": state["task_id"],
        "plans": state["scored_plans"],
        "recommended": state["scored_plans"][0],
        "explanation": state["plan_explanation"],
    })
    return {"confirmation": decision}
```

确认接口 `POST /api/v1/scheduling/tasks/{task_id}/confirm`，请求体：

```json
{ "approved": true, "plan_id": "A", "adjustments": [] }
```

恢复执行：

```python
await graph.ainvoke(
    Command(resume={"approved": True, "plan_id": "A"}),
    config={"configurable": {"thread_id": task_id}}
)
```

### 4.4 异常重排机制

**异常来源**：车辆故障、司机缺勤；门店临时加货／减货；交通管制、天气；地形临时管控。

**重排策略**

1. 锁定已执行趟次，不重排
2. 只重排未执行、未完成部分
3. 优先局部修复，失败再全局重排
4. 记录 `replan_count`，避免无限循环
5. 支持自动重排和人工触发

## 十、项目难点 📄

随堂笔记原文本节只有标题、无正文。以下为技术方案文档的"关键技术风险与应对"：

| 难点 / 风险 | 应对措施 |
| --- | --- |
| 求解规模大、耗时长 | 启发式先出可行解，CP-SAT 局部优化；分时段、分区域求解 |
| 规则复杂、冲突多 | 规则中心版本化、冲突检测、试算、优先级 |
| 人工确认流程长 | 默认推荐方案，支持一键确认；异常时再人工介入 |
| LLM 解释不准确 | 硬约束不交给 LLM；Prompt 严格约束；LangSmith 评估 |
| 下发重复 | 幂等设计：`task_id + plan_id + trip_id` 唯一 |
| 异常重排死循环 | `replan_count` 限制；锁定已执行任务 |
| 数据不一致 | 数据快照 + 规则版本快照；事务保证 |
| TMS 对接不稳定 | 重试、熔断、补偿；消息队列异步 |

**核心设计原则** 📄

1. 硬约束代码化：最低装载量、趟次、地形、线路、时段规则由确定性代码和求解器保证。
2. LLM 只做解释和辅助：方案解释、报告、自然语言规则解析。
3. 多方案比选 + 人工确认：真实商业项目必须有人工确认环节。
4. 规则版本化：每次调度记录规则版本，保证可追溯。
5. 混合求解：启发式快速出解，CP-SAT 精确优化。
6. 异常可重排：锁定已执行任务，局部优先修复。
7. 与 TMS 闭环：调度结果下发 TMS，执行结果回传，形成闭环。

## 十一、验收标准 ✎

技术方案文档要求"需求文档"须包含验收标准，但两份文档均未给出具体指标。以下为按需求明细推导的建议：

| 需求 | 建议验收方式 |
| --- | --- |
| 门店需求必须全部满足 | 对账：方案覆盖门店数 = 当日有货量门店数 |
| 达到最低装载量才发车 | 校验所有已发车趟次 `load_amount >= min_load` |
| 不超最高装载量 | 校验 `load_amount <= max_load` |
| 上午门店上午送、下午门店下午送 | 校验 `store.delivery_window` 与 `plan_detail.time_window` 一致 |
| 地形能力匹配 | 校验 `vehicle_terrain_capability` 覆盖门店 `terrain_type` |
| 线路匹配 | 校验门店属于车辆线路（`store_route_mapping`） |
| 趟次上限 | 四米二／大包 ≤ 2 趟，小包 ≤ 4 趟 |
| 货量不足优先保障大包、小包 | 货量不足场景下，大包／小包趟次达成率 = 100% |
| 优先用四米二 | 同等条件下方案的四米二使用率高于其他车型方案 |
| 多方案比选 | 每次调度产出 A/B/C/D 四套方案 + 评分 + 解释 |
| 人工确认 | 未确认前不下发；确认后写入 `scheduling_confirmation` |
| 异常重排 | 已执行趟次不被修改；`replan_count` 有上限 |
| 下发幂等 | 同一 `task_id + plan_id + trip_id` 重复调用不产生重复任务 |
